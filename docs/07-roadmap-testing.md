# 로드맵과 테스트

## 1. 1인 개발 로드맵

| 기간 | 목표 | 완료 조건 |
| --- | --- | --- |
| 1~2주 | 모노레포·CI·AWS 기반 | 웹·API 기본 빌드, staging health check, 기존 Expo 회귀 검사 |
| 3주 | 인증 | 카카오·Apple·Google 로그인과 계정 삭제 |
| 4~5주 | 여행·초대 | 여행 생성, 3~6인 가입, 권한 테스트 |
| 6주 | 기존 일정 | 장소 검색·직접 입력·일정 버전 발행 |
| 7주 | 비공개 선호 | 본인 CRUD, 제출 현황, 개인정보 테스트 |
| 8주 | 날씨·신고 | 30분 폴링, 중복 방지, 수동 신고 |
| 9~10주 | 후보·공정성 | 외부 API, 점수 계산, Bedrock 제한 호출 |
| 11주 | 투표·적용 | 익명 투표, 12시간 마감, 새 일정 버전 |
| 12~13주 | 웹 UX | UI 시안 반영, 인앱 알림함, WCAG 2.2 AA |
| 14~16주 | 웹 공개 베타 | 보안·성능·브라우저 E2E·운영 훈련 |
| 웹 베타 후 | 모바일 제품화 | 웹 MVP 기능 이식, 푸시·딥링크·접근성·스토어 심사 |

모바일 제품화와 Docker/ECS 전환은 웹 베타 안정화 후 별도 일정으로 수행한다.

이 표는 출시 단위 로드맵으로 유지한다. 다음 10개 개발일의 0.25~1일 단위 작업과 증거는 [0~1단계 실행 백로그](./08-execution-backlog.md)에서 관리한다.

## 2. 테스트 계층

### 단위 테스트

- 날씨 60% 경계값과 일정 시간 겹침
- 멤버별 만족도, 최저 만족도 정렬, 양보 원장 감쇠
- 동률 투표와 안정적 최종 정렬
- 여행 인원·초대 만료·역할 권한
- 일정 버전과 투표 마감 계산

### 통합·계약 테스트

- Testcontainers PostgreSQL과 Flyway 전체 마이그레이션
- WireMock으로 TourAPI·기상청·ODsay·Bedrock 정상·지연·오류·한도 초과
- Spring OpenAPI와 생성 TypeScript 클라이언트 호환성
- SQS 중복 전달·재시도·DLQ와 outbox 멱등성
- 전원 투표 즉시 마감, 1분 마감 작업, 0표 취소와 동일 세트 중복 마감
- 마감 코어는 전원 참여·기한 경계·동률·stale·원자적 양보 원장 갱신을 Testcontainers로 검증하고, 1분 스케줄 배송은 EventBridge/SQS 연결 후 별도로 검증한다.
- 다른 멤버의 선호·투표를 조회할 수 없는지 확인하는 부정 테스트

### E2E

- 1차 공개 베타는 Playwright로 로그인부터 일정 확정까지 웹 핵심 시나리오를 검증한다.
- 모바일 개발을 재개하면 Maestro로 같은 핵심 시나리오를 추가하고 iOS·Android production build에서 로그인 redirect, 초대 딥링크, 푸시를 확인한다.
- 모바일 네트워크 중단·재연결 검증은 후속 모바일 출시 게이트에서 수행하며 웹 베타를 막지 않는다.

### 비기능 테스트

- 후보 생성 p95 60초, 일반 API p95 500ms 목표
- 50개 동시 그룹의 투표·조회 부하
- 웹 WCAG 2.2 AA. VoiceOver·TalkBack 핵심 흐름은 후속 모바일 출시에서 검증
- OWASP API 권한, rate limit, secret scan, 의존성 취약점 검사

## 3. 대표 인수 시나리오

1. 방장이 대전 3일 여행을 만들고 기존 야외 일정 3개를 등록한다.
2. 초대 링크로 멤버 3명이 로그인·가입한다.
3. 네 명 모두 비공개 선호를 제출하고 그룹에는 완료 여부만 보인다.
4. 향후 24시간 야외 슬롯의 강수확률 60% 예보가 들어와 한 번만 알림이 생긴다.
5. 멤버가 재조정에 동의하고 60초 안에 검증된 후보 1~3개가 나온다.
6. 네 명의 투표 선택은 숨겨지고 득표수와 참여 인원만 표시된다.
7. 동률이면 양보 원장 규칙이 항상 같은 후보를 선택한다.
8. 확정 결과가 새 일정 버전으로 적용되고 원본 버전도 조회 가능하다.
9. 여행 종료 30일 후 원본 선호와 개인 투표가 삭제된다.

## 4. 실패 인수 시나리오

- TourAPI 결과가 없으면 직접 입력과 원본 일정 유지 경로를 제공한다.
- ODsay 장애 시 이동시간을 `정보 없음`으로 표시하고 검증 불가능한 후보를 자동 확정하지 않는다.
- Bedrock 장애 시 코드 후보와 템플릿 설명으로 투표를 계속할 수 있다.
- 같은 재조정 요청·SQS 메시지가 반복되어도 후보 세트는 하나만 생성된다.
- 일정 버전이 바뀐 뒤 오래된 후보를 적용하려 하면 취소되고 새 재조정을 요구한다.
- 투표가 0표로 마감되면 일정을 변경하지 않는다.

## 5. 출시 게이트

- 공개 베타 핵심 E2E가 지원 웹 브라우저에서 모두 통과한다.
- P0/P1 결함, DLQ 메시지, 알려진 개인정보 노출이 0건이다.
- 계정 삭제와 30일 데이터 삭제를 staging에서 실제로 검증한다.
- 외부 API 키·할당량·이용조건, Bedrock 모델 접근, ODsay 6개월 종료일을 운영 문서에 기록한다.
- RDS 복구와 Beanstalk 롤백 훈련을 완료한다.
- 개인정보처리방침과 이용약관을 준비한다. 앱스토어 개인정보 라벨과 심사 계정은 후속 모바일 출시 전에 준비한다.

## 6. 후속 우선순위

1. React Native 앱 기능 동등성, 푸시·딥링크·스토어 출시
2. Docker/ECS Fargate 이전과 다중 인스턴스 운영
3. 웹 푸시·이메일 알림
4. WebSocket 또는 SSE 실시간 투표
5. 검증 가능한 휴관·교통 자동 감지
6. 대전 운영 데이터가 충분할 때 다른 국내 지역 확장
