# UX와 화면 흐름

## 1. 디자인 방향

기존 시안의 따뜻한 녹색·노란색, 큰 라운드 카드, 충분한 여백, 친근한 캐릭터를 유지한다. 웹과 앱은 정보 구조와 기능을 공유하지만 화면 컴포넌트 구현은 공유하지 않고 색상·간격·타이포그래피·아이콘 의미만 `design-tokens` 패키지로 공유한다.

접근성 기준은 웹 WCAG 2.2 AA, 앱의 VoiceOver·TalkBack 지원이다. 색만으로 선택·경고 상태를 표현하지 않고 아이콘과 텍스트를 함께 사용한다.

## 3. 추가 화면

### 로그인

- 카카오, Apple, Google 버튼을 제공한다.
- 약관·개인정보처리방침 링크와 계정 삭제 경로를 노출한다.
- 초대 링크에서 진입했다면 로그인 완료 후 원래 여행 가입 화면으로 복귀한다.

### 기존 일정 편집기

- 날짜 탭과 시간순 슬롯 목록을 제공한다.
- 장소 검색은 TourAPI 결과를 우선하며 직접 입력을 항상 제공한다.
- 슬롯 필드는 시작·종료 시각, 장소, 실내·실외, 범주, 예상 1인 비용, 메모다.
- 시간 중복, 종료가 시작보다 빠른 경우, 대전 밖 좌표는 저장 전에 막는다.

### 변수 알림·신고

- 자동 날씨 알림은 영향받는 슬롯, 강수확률, 예보 발표 시각을 보여준다.
- 수동 신고 종류는 `휴관`, `교통`, `기타`이며 자유 입력은 200자로 제한한다.
- 알림만으로 일정을 변경하지 않고 `재조정 시작` 또는 `유지`를 선택하게 한다.

### 생성 진행·실패

- `후보 검색 → 이동시간 확인 → 공정성 계산 → 설명 생성` 단계를 표시한다.
- 60초를 넘으면 백그라운드 진행 안내와 알림 수신 옵션을 보여준다.
- 외부 API 실패, 후보 부족, 정보 없음은 각각 다른 복구 행동을 제공한다.

### 알림함

- 첫 세로 슬라이스는 그룹 투표로 일정이 확정된 알림을 시간순으로 제공한다. 날씨 감지, 후보 준비, 마감 임박 알림은 후속 범위다.
- 읽지 않음·읽음을 텍스트와 배지로 함께 구분하고, 읽음 처리는 서버에서 동기화한다.
- 일정 확정 알림을 선택하면 읽음 처리 후 해당 여행의 확정 후보 결과로 이동한다.

## 4. 반응형 규칙

- 모바일 앱과 767px 이하 웹은 단일 열·하단 내비게이션을 사용한다.
- 768px 이상 웹은 최대 720px 콘텐츠 열과 좌측 내비게이션을 사용한다.
- 후보 비교는 모바일에서 가로 스냅 카드, 데스크톱에서 최대 3열 카드로 표시한다.
- 핵심 행동 버튼은 모바일 하단 안전영역 위에 고정하되 키보드가 열리면 입력을 가리지 않는다.

## 5. 화면 상태 기준

모든 데이터 화면은 `loading`, `empty`, `error`, `stale`, `offline`, `permission-denied` 상태를 가진다. 낙관적 투표 갱신은 실패 시 원래 선택으로 되돌리고 오류를 안내한다. 일정 편집 충돌은 자동 병합하지 않고 최신 버전과 사용자의 입력을 비교해 다시 저장하게 한다.

## 6. 핵심 문구 원칙

- `AI가 바꿨어요` 대신 `그룹 투표로 일정이 변경됐어요`를 쓴다.
- 공정성 설명은 개인을 지목하지 않고 `이전에 덜 반영된 의견에 가중치를 적용했어요`처럼 집단 수준으로 표현한다.
- API에서 확인하지 못한 운영시간·가격은 `정보 없음`과 확인 시각을 표시한다.
- 자동 감지는 확정이 아니라 제안임을 모든 알림에서 명시한다.
