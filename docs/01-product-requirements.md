# 제품 요구사항

## 1. 제품 정의

다정은 대전에서 함께 여행 중인 3~6명이 기존 일정을 조정해야 할 때, 날씨·동선·예산·피로도·취향과 과거 양보 이력을 반영한 대체안 3개를 제시하고 익명 투표로 공정한 합의를 돕는 서비스다.

### 해결할 문제

- 변수 자체보다 같은 사람이 반복해서 양보하는 문제가 자주 발생한다.
- 단체 채팅에서 각자의 예산과 피로도를 공개하기 어렵다.
- 장소 검색, 이동시간 비교, 의견 취합이 분산되어 합의가 늦어진다.

### 성공 지표

| 지표 | 목표 |
| --- | --- |
| 합의 시간 | 재조정 시작 그룹의 90%가 10분 안에 일정 확정 |
| 후보 생성 | p95 60초 이내 |
| 개인정보 | 원본 선호·개인 투표의 다른 멤버 노출 0건 |
| 신뢰성 | 확인하지 못한 장소 정보의 임의 추정 0건 |
| 웹 품질 | 지원 브라우저의 공개 베타 핵심 E2E 통과율 100% |

12시간은 투표의 최대 운영 기한이다. 10분 지표는 구성원들이 실제로 참여한 그룹의 합의 속도를 측정한다.

## 2. 범위

### MVP에 포함

- 카카오·Apple·Google 로그인
- 여행 기본정보와 기존 일정 직접 등록
- TourAPI 장소 검색과 직접 입력 장소
- 초대 코드·링크를 통한 3~6인 그룹 참여
- 개인 선호·예산·피로도·이동 성향 비공개 제출
- 기상청 강수확률 기반 변수 자동 감지
- 휴관·교통·기타 문제 수동 신고
- 결정론 코드와 Bedrock을 조합한 재조정 후보 생성
- 후보 1~3개 비교, 익명 투표, 공정한 동률 처리
- 확정 일정의 새 버전 생성과 변경 사유 표시
- 웹 인앱 알림

### 출시 순서

- 1차 공개 베타는 반응형 Next.js 웹으로 핵심 사용자 여정 전체를 제공한다.
- React Native 앱은 웹 MVP가 안정화된 뒤 같은 API·권한·상태 계약을 사용해 후속 출시한다.
- 모바일 기능을 미루는 동안 기존 Expo 프로젝트의 lint·typecheck·export 회귀 검사는 유지한다.

### 명시적 비목표

- 처음부터 전체 여행 일정을 생성하지 않는다.
- 숙소를 추천하거나 변경하지 않는다.
- 예약·결제·환불을 대행하지 않는다.
- 맛집의 메뉴 취향까지 중재하지 않는다. 장소 범주와 동선만 반영한다.
- AI가 그룹 승인 없이 일정을 바꾸지 않는다.
- 실시간 교통정체·임시 휴관을 자동 감지한다고 약속하지 않는다.
- 대전 외 지역, 해외, 한국어 외 언어를 지원하지 않는다.
- iOS·Android 네이티브 앱, 앱 푸시, 딥링크, 앱스토어 출시는 1차 웹 공개 베타의 완료 조건에 포함하지 않는다.

### 후속 모바일 범위

- 웹 MVP의 로그인, 여행·초대, 일정, 재조정, 투표·확정 흐름을 Expo 앱으로 확장한다.
- Expo Push, 초대 딥링크, SecureStore 기반 인증, VoiceOver·TalkBack, iOS·Android E2E와 스토어 심사를 완료한다.
- 모바일 전용 구현은 공용 OpenAPI 계약을 바꾸지 않으며 플랫폼별 UI 컴포넌트는 공유하지 않는다.

## 4. 핵심 사용자 여정

1. 사용자가 소셜 로그인 후 여행을 만들거나 초대 링크로 참여한다.
2. 방장이 날짜·시간과 장소를 직접 등록해 기존 일정을 만든다.
3. 각 멤버가 다른 사람에게 보이지 않는 선호 설문을 제출한다.
4. 시스템이 향후 24시간 야외 일정에서 강수확률 60% 이상을 감지하거나 멤버가 문제를 신고한다.
5. 시스템은 알림만 보내고, 멤버가 `재조정 시작`에 동의해야 후보 생성을 시작한다.
6. 후보가 준비되면 멤버는 설명과 이동·예산·피로 정보를 비교하고 한 후보에 투표한다.
7. 전원이 투표하거나 12시간이 지나면 집계한다. 동률이면 양보 원장 가중 규칙으로 결정한다.
8. 승리한 후보를 새 일정 버전으로 적용하고 무엇이 왜 변경됐는지 그룹에 공개한다.

## 5. 기능 요구사항

### 계정·그룹

- `FR-AUTH-01`: 모든 보호 API는 Cognito JWT를 요구한다.
- `FR-TRIP-01`: 한 여행은 방장 1명과 총 3~6명의 활성 멤버를 가진다.
- `FR-INVITE-01`: 초대 코드는 7일 후 만료되며 방장이 재발급하면 이전 코드는 즉시 폐기된다.
- `FR-INVITE-02`: 초대받은 사용자는 로그인 후에만 여행에 가입한다.

### 일정·선호

- `FR-PLAN-01`: 장소 검색 결과가 없어도 방장은 이름·주소·좌표·예상 비용을 직접 입력할 수 있다.
- `FR-PLAN-02`: 일정 수정은 낙관적 잠금으로 보호하고 충돌 시 최신 버전을 다시 불러오게 한다.
- `FR-PREF-01`: 그룹에는 제출 완료 여부만 공개하고 원본 응답은 본인에게만 반환한다.
- `FR-PREF-02`: 예산, 활동 강도, 이동 허용도, 선호 범주, 중요 기준 최대 2개를 받는다.

### 변수·후보·투표

- `FR-DISRUPT-01`: 같은 일정 슬롯과 예보 시각에 대해 중복 날씨 알림을 만들지 않는다.
- `FR-REPLAN-01`: 후보 생성 요청은 비동기로 처리하고 진행 상태를 조회할 수 있어야 한다.
- `FR-REPLAN-02`: 검증된 후보가 3개 미만이면 실제 확보한 수만 보여준다.
- `FR-VOTE-01`: 한 사람은 후보 세트마다 한 표를 가지며 마감 전에는 변경할 수 있다.
- `FR-VOTE-02`: 집계 수치는 공개하지만 사용자가 무엇을 선택했는지는 공개하지 않는다.
- `FR-APPLY-01`: 확정안은 기존 일정을 덮어쓰지 않고 새 버전을 만든다.

## 6. 개인정보와 보존

- 원본 선호, 피로도, 예산, 개인 투표는 민감 데이터로 분리한다.
- 해당 값은 그룹 응답, 애플리케이션 로그, 분석 이벤트, Bedrock 프롬프트에 포함하지 않는다.
- RDS 저장장치와 백업은 KMS로 암호화하고 전송은 TLS만 허용한다.
- 여행 종료 30일 후 원본 선호와 개인 투표를 삭제하고 익명 집계만 유지한다.
- 계정 삭제 시 개인 데이터는 삭제하고 공동 일정 이력에는 `탈퇴한 멤버`로 익명화한다.

## 7. 분석 이벤트

`trip_created`, `member_joined`, `preference_completed`, `disruption_detected`, `replan_started`, `proposal_ready`, `vote_cast`, `consensus_reached`, `itinerary_applied`, `integration_failed`를 기록한다. 이벤트에는 사용자 원본 응답, 장소 자유입력 메모, 프롬프트 내용을 넣지 않는다.
